# WEB-001. Контракт пространственно-временного анализа

Статус: DONE (19.09.2026). Приоритет: P0. Область: backend, frontend, данные. Критерии: R1, R2, R3.

Зависимости: нет. Разблокирует: WEB-002–009.

## Цель и проблема

Сейчас даты, регион и bbox используются разными частями системы независимо. Зафиксировать одну модель запроса и результата, по которой реализуются карта, справка, экспорт и интеграция результатов обработки сцен.

## Что сделать

1. Проверить и финализировать [analysis-contract.md](analysis-contract.md). Считать его исходным предложением, а не существующей реализацией.
2. Описать Pydantic-схемы запроса, каталога наборов, результата анализа, provenance, coverage, warnings и ошибок. Согласовать с TypeScript-типами; использовать доступный способ предотвращения их расхождения: генерацию или контрактные тесты.
3. Зафиксировать UTC, включённость конечной даты, временной отбор термоточек и гарей. Принятый v1-вариант для гарей — дата послепожарной съёмки с явным пояснением пользователю.
4. Описать правила повторных оценок одной гари, Polygon/MultiPolygon и частичного пересечения AOI.
5. Зафиксировать классы 1/2/3, единицы измерения, `null` и нули, точность и правила округления.
6. Разделить покрытие AF/термоточек и BS: отсутствие одного источника не должно обнулять другой. Указать, какие площади доступны для расчёта coverage, а какие неизвестны.
7. Зафиксировать версионирование набора и алгоритма, состав детерминированного `result_id` и поведение экспорта при несовпадении версии.
8. Определить конфигурируемые ограничения bbox/периода/объёма результата. Измеренные значения уточнить в WEB-004 и записать в документацию.
9. Добавить контрактные примеры: нормальный ответ, частичное покрытие, пустое наблюдение, нет покрытия, нет валидных пикселей, ошибка валидации.

## Артефакты и точки изменений

- Финализированный `docs/tasks/analysis-contract.md`; при переносе в `docs/data/` оставить ссылку и не создавать две расходящиеся спецификации.
- Новые схемы, например `backend/app/schemas/analysis.py`, и соответствующие типы `frontend/src/lib/api/`.
- JSON-фикстуры контрактных ответов в тестах. Синтетические фикстуры явно пометить `synthetic_demo`.
- Не ломать существующий `FeatureCollection` и старые API: расширение вводить явно.

## Критерии приёмки

- [ ] Для каждого поля указаны тип, обязательность, единицы, допустимость `null` и смысл.
- [ ] Можно однозначно понять, почему конкретная точка/гарь входит или не входит в заданный период.
- [ ] Запрос фиксирует версию данных; одна версия не меняется на месте.
- [ ] Значения в справке выводятся из тех же зон, которые будут экспортироваться.
- [ ] Описано различие «не обнаружено», «не обследовано», «закрыто облаками».
- [ ] Все контрактные примеры валидируются backend-схемами; frontend способен их прочитать.
- [ ] Новая схема не выдаёт существующие эвристические confidence/priority за метрики качества модели.

## Проверки

Проверить `from > to`, некорректную дату, нулевой/перевёрнутый bbox, NaN/Infinity, координаты за пределами WGS84, одну календарную дату, момент ровно на правой временной границе, известный и неизвестный class_id. Проверить нормализацию эквивалентных запросов и стабильность ID.

## Вне задачи

Реальные георасчёты, дизайн экрана, очередь фоновых задач, произвольный полигон. Не обещать скорость до замера на данных.
